# 项目结构与数据流程讲解稿

**建议时长：约 4—5 分钟。** 演示时可同时打开项目目录和网页，按下文提示切换画面。

## 开场：项目要解决什么

大家好，我介绍的项目是“Web 日志异常与审计程序”。Web 服务每天会产生大量访问记录。单看原始日志，我们能看到请求时间、路径和状态码，但很难迅速判断哪些记录值得复核；如果系统只显示一条“异常告警”，又说不清它由哪些请求触发。因此，这个项目把工作分成三步：先整理日志，再产生带证据的候选告警，最后由人记录处置结果。它是一个在本机运行的离线分析工具，重点是让判断过程可以追溯。

## 第一部分：项目结构为什么这样设计

【展示项目目录】

项目可以看作四层。第一层是 `public/`，其中 `index.html` 定义页面内容，`style.css` 负责样式，`app.js` 处理文件导入、图表、告警筛选、人工处置和导出。浏览器只负责交互，不在页面中实现检测规则。

第二层是 `server.js`。它提供本地 HTTP 接口：接收日志、返回分析报告、读取历史记录，以及接收告警处置。服务只监听 `127.0.0.1`，分析结果写入项目的 `data/` 目录。把接口和页面分开，方便以后替换界面，同时保持分析入口一致。

第三层是 `analyzer.js`，这是核心业务模块。它负责把不同格式的日志变成统一事件，隔离无效记录，运行单条请求规则和滚动时间窗口规则，最后生成统计信息和告警。规则集中在这个文件里，测试时可以直接调用，不必先启动网页。

第四层是验证材料。`analyzer.test.js` 检查解析、去重、时间转换和跨分钟窗口；`eval.js` 用固定的合成会话计算评价指标；`docs/` 记录数据契约、评价口径和交付边界。这样，代码回答“程序怎样做”，测试和文档回答“凭什么相信它按约定做了”。

## 第二部分：一条日志怎样流过系统

【打开网页，点击“加载示例日志”】

现在沿着一条日志看数据流程。第一步，用户在浏览器选择文件。`app.js` 读取文本，发给 `server.js` 的分析接口。服务端检查请求内容后，把整份日志交给 `analyzer.js`。

第二步是解析与规范化。分析器支持 JSONL，也支持常见的 Nginx、Apache Common 和 Combined 格式。它把时间统一转换为 UTC，提取事件 ID、服务、请求路径、状态码、会话和来源等字段。旧日志没有事件 ID 时，会根据数据集哈希和行号生成稳定 ID。坏行、无效时间和重复事件 ID 不会悄悄消失，而是进入报告的 `rejected` 列表，留下行号、原因和原始文本。

第三步是检测。单条请求规则寻找疑似 SQL 注入、XSS、路径穿越、敏感路径和扫描器特征。聚合规则按服务与会话分组；如果没有会话字段，就按来源 IP 分组。它使用事件时间计算滚动 60 秒窗口。例如，一个会话在 60 秒内出现 5 次符合条件的登录失败，就会形成一条候选告警。告警不仅记录规则名称，还记录触发它的事件 ID 集合、规则版本和分组依据。这里的 IP 只是网络来源线索，不能直接当作人的身份。

第四步是保存和展示。`server.js` 为这次运行保存一份 JSON 报告，包含数据集 ID、运行 ID、规范化事件、隔离行、统计结果和告警。网页读取报告，展示请求量、状态码分布、重点来源和异常事件。点击告警后，分析人员可以用事件 ID 在导出的 JSON 中回查原始记录，因此一条告警能回答“从何而来”。

第五步是人工处置。告警初始状态为 `NEW`，可以进入 `TRIAGED`，之后由人标为 `CONFIRMED` 或 `DISMISSED`，最后 `CLOSED`。每次转换都要填写操作人和理由，服务端保存前后状态与时间。规则给出的是候选判断，最终处置要结合业务背景；例如高频请求也可能是事先批准的压测。

## 第三部分：怎样验证设计有效

【展示终端中的 `npm test` 和 `npm run eval`】

我从两个层面验证。第一是回归测试：用固定输入检查日志能否解析、重复 ID 是否隔离、旧版与新版时间是否一致，以及 60 秒窗口能否跨过整分钟边界。第二是合成数据评价：`eval.js` 构造四个完整会话，包括正常浏览、失败登录、404 探测和已批准的高频压测。评价按会话统计 TP、FP、FN、TN，而不是把每条日志都算作一次检出。固定规则会把压测报成候选异常，这个反例说明“检测到高频”并不等于“确认攻击”。

项目的结构也对应了这一点：`source_label` 只供评价时使用，不进入分析器的告警决策；检测输出和人工结论分开保存。现有合成集很小，只能说明计算流程可复现，不能据此宣称真实环境下的准确率。

## 结束：设计取舍与边界

最后总结一下：这个项目的主线是“原始日志、规范化事件、规则告警、关联证据、人工处置”。前端负责展示和操作，服务端负责接口与保存，分析器负责确定性的规则，测试与评价脚本负责复核。这种设计适合单机、离线、可重复的课程演示。当前版本没有多用户认证，也没有加密存储或真实业务基线；如果要用于多人协作或生产环境，需要先补这些能力，并重新校准规则阈值。
