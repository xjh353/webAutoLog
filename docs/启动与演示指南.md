# 项目启动与演示指南

> **这份文档回答**：演示前要检查什么、现场按什么顺序操作、终端补充演示哪些、常见问题怎么答——是一份可直接照着走的演示脚本。

这份指南用于在自己的电脑或课堂现场展示 Web 日志异常与审计程序。建议先按“演示前检查”走一遍，再按照“现场演示顺序”操作。默认演示只使用项目自带的合成日志，不需要真实网站日志。

## 一、演示前检查

### 1. 准备环境

项目需要 **Node.js 18 或更新版本**，无需安装第三方 npm 依赖。在 PowerShell 中进入项目目录：

```powershell
cd C:\Users\lcx20\Desktop\webLog
node --version
npm --version
```

如果是在另一台电脑上，先克隆仓库，再进入克隆后的目录：

```powershell
git clone https://github.com/xjh353/webAutoLog.git
cd webAutoLog
```

确认目录里有 `package.json`、`src/` 和 `public/`。项目启动命令来自 `package.json`，实际执行的是 `node src/server/server.js`。

### 2. 启动本地服务

```powershell
npm start
```

终端应显示 `Web 日志审计工作台运行于 http://127.0.0.1:3000`。保持这个终端窗口运行，在浏览器打开 <http://127.0.0.1:3000>。看到“Web 日志安全总览”和“加载示例日志”按钮，说明页面和本地服务已连通。

演示结束时回到终端按 `Ctrl+C` 停止服务。如果 3000 端口被占用，可在**当前 PowerShell 窗口**改用其他端口：

```powershell
$env:PORT = 3001
npm start
```

随后打开 <http://127.0.0.1:3001>。端口设置只作用于当前终端会话。

## 二、现场演示顺序（约 5—7 分钟）

### 第一步：导入示例日志

在首页点击 **“加载示例日志”**。页面会自动完成导入和分析，顶部出现当前文件名，随后显示四项核心统计。当前版本的内置示例应得到 **102 条有效请求、23 条异常事件、5 条高危事件、31.4% 错误请求占比**。示例日志由 `src/server/server.js` 的 `demoLog()` 生成，包含正常访问、重复登录失败、404 探测、敏感路径请求、疑似注入和 5xx 错误。

**讲解提示：**“这里展示的是可疑线索数量，不是已经确认的攻击次数。每条告警都需要查看触发它的原始请求。”

### 第二步：讲解总览统计

在“安全总览”中依次指向总请求数、异常事件数、高危事件数、错误请求占比、按分钟绘制的请求流量趋势、HTTP 状态码分布和重点来源 IP。说明这些统计用于定位需要先看的时间段和来源；IP 只代表日志中的网络来源，不能直接代表个人身份。

**讲解提示：**“总览负责缩小排查范围，真正的判断要进入具体告警和证据。”

### 第三步：查看告警与原始证据

点击左侧 **“异常事件”**。先把级别筛选为“高危”，再点开任意一条告警的 **“查看原始证据”**。页面会显示关联事件 ID、原始日志行号和原始文本。可以搜索 `203.0.113.27` 查看登录失败相关记录，也可以搜索“疑似 SQL 注入”查看对应规则的告警。

重点说明告警中的 `eventIds` 与报告 `events` 一一对应，规则版本随告警保存。页面用文本方式显示原始路径，即使日志里包含 HTML 或命令样文字，也只是待核查的数据。

**讲解提示：**“一条告警可以回到触发它的具体日志行，这就是项目强调的证据链。”

### 第四步：演示人工处置

找到一条尚未处置的告警，点击 **“分诊”**。按提示填写操作人和理由，例如操作人“演示复核员”，理由“已查看关联事件，等待进一步确认”。再根据演示情境选择 **“确认”** 或 **“排除”**，填写第二次理由。展开该告警的 **“处置记录”**，展示每次操作的前后状态、时间、操作人和理由。

处置路径是 `NEW → TRIAGED → CONFIRMED/DISMISSED → CLOSED`。服务端会拒绝跳过分诊等非法状态转换。当前操作人只是手动填写的标识，系统没有账号认证；现场演示时不要把它解释成已验证身份。

**讲解提示：**“程序负责提出候选异常并保留证据，确认与排除由人做出并留下理由。”

### 第五步：查看历史与导出

点击左侧 **“分析记录”**，找到刚才的示例报告并重新打开。报告保存在本机 `data/` 目录，因此刷新页面后仍能读取。返回“异常事件”，点击 **“导出 JSON”** 或 **“导出 CSV”**。JSON 含完整报告和原始事件；CSV 含完整告警列表，包括当前页面未显示的后续条目。

**讲解提示：**“历史报告保留分析当时的规则版本和处置轨迹；导出文件可能带有敏感路径或会话标识，分享前应核查。”

## 三、终端补充演示（约 2—3 分钟）

在另一个 PowerShell 窗口进入项目目录，运行：

```powershell
npm test
```

测试覆盖旧新版日志解析、坏行与重复 ID 隔离、60 秒窗口端点、批准清单的作用范围、报告持久化和人工处置接口。测试项数量可能随项目更新而变化，现场应以实际输出中的 `pass`、`fail` 为准。

接着运行：

```powershell
npm run eval
```

脚本用 `fixtures/` 中的固定合成情境比较 P2-R1 与 P2-R2。它按**完整会话**计算 TP、FP、FN、TN 和 Precision、Recall、FPR；标签只用于评价，不传给分析器。当前测试分区中，P2-R1 的误报会话为 1，P2-R2 为 0，两者目标异常漏报均为 0。每个分区只有四个合成会话，这些数字只能说明该实验可复现，不能当作真实业务准确率。

如果需要保存一次可交接的实验包，运行：

```powershell
npm run experiment
```

命令会在 `data/experiments/` 生成输入、两版完整报告和 `result.json`。现场可打开 `result.json` 说明数据集哈希、规则版本、逐次运行结果、评价分母和已知限制。

## 四、常见问题

| 现象 | 检查方法 |
| --- | --- |
| 浏览器打不开页面 | 确认 `npm start` 仍在运行，地址是 `127.0.0.1` 和终端显示的端口。 |
| 提示端口占用 | 在当前 PowerShell 窗口设置其他 `PORT`，重新启动。 |
| 导入后没有有效记录 | 检查日志是否为 JSONL 或 Common/Combined 格式，是否含可解析时间和 HTTP 状态码；坏行会在报告中列出。 |
| 页面有告警，但无法确认是否攻击 | 展开原始证据，并结合业务、服务错误日志和已批准测试记录人工复核。 |
| 电脑上找不到报告 | 首次成功分析后才会创建 `data/`；它被 Git 忽略，不会随仓库克隆到另一台电脑。 |

## 五、演示结束时的总结话术

“这套程序从一份日志出发，把原始行规范化为事件，再通过请求规则和滚动窗口产生候选告警。告警保留事件 ID、规则版本和原始证据，分析人员可以分诊、确认或排除并留下理由。测试和固定合成数据让规则行为可以重复检查。它适合单机离线复盘和课程展示；真实业务采用前，还需要身份认证、数据保护以及更充分的规则校准。”
