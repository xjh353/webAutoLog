# 项目结构设计与文件职责讲解

这份文档适合在展示项目目录时使用。项目的主线是：**浏览器导入日志 → 服务端接收 → 分析模块解析并检测 → 保存可追溯报告 → 浏览器展示与人工处置**。目录按职责划分，页面、接口、分析规则和评价材料各自有明确位置。

## 一、先看项目全貌

```text
webLog/
├── src/                 程序核心：分析、告警对象、公共常量和本地服务
│   ├── analysis/        日志解析、规范化、检测和报告生成
│   │   └── rules/       单条请求规则与时间窗口规则
│   ├── core/            多模块共用的常量和哈希工具
│   ├── domain/          告警的数据结构
│   └── server/          HTTP 接口和本地报告读写
├── public/              浏览器页面、交互脚本和样式
├── fixtures/            固定的合成评价情境与批准清单
├── scripts/             评价和实验运行脚本
├── tests/               解析、规则、实验和接口测试
├── docs/                设计、规则、评价、交付及讲解材料
├── data/                运行后产生的本地报告，不提交到 Git
├── package.json         启动、测试和评价命令
└── README.md            项目入口和快速使用说明
```

### 为什么按这些目录划分

`public/` 只处理用户看见和操作的内容；`src/server/` 处理浏览器请求和文件保存；`src/analysis/` 负责“这条日志意味着什么”；`tests/` 和 `fixtures/` 让检测结果能重复验证。这样修改页面样式不会改动规则，调整规则也可以先运行测试和实验，再决定是否用于网页默认流程。项目目前使用 Node.js 内置模块，没有数据库或第三方运行依赖，适合单机离线分析。

## 二、`src/`：程序实际工作的地方

### `src/analysis/`：从日志到报告

| 文件 | 主要职责 | 何时被调用 |
| --- | --- | --- |
| `parser.js` | 读取 JSONL 与 Common/Combined 日志，提取字段并转换 UTC 时间；保留来源地址字段的出处。 | 导入后，逐行解析时 |
| `normalizer.js` | 给旧日志补稳定事件 ID，隔离格式错误、无效时间和重复 ID，形成有效事件与隔离记录。 | 解析之后、规则检测之前 |
| `analyzer.js` | 分析总入口，选择 P2-R1 或 P2-R2，调用规则并汇总告警及被抑制的候选告警。 | 服务端分析接口或评价脚本调用时 |
| `metrics.js` | 统计状态码、每分钟请求量、来源 IP 和告警数量。 | 生成报告时 |
| `report-builder.js` | 将数据集 ID、规则版本、事件、隔离行、告警和统计值装配成完整报告。 | 一次分析即将结束时 |

`rules/` 是 `analysis/` 的子目录。`request-rules.js` 检查单条请求，例如疑似 SQL 注入、XSS、路径穿越、敏感路径和扫描器 User-Agent。`window-rules.js` 按会话或来源 IP 对有效事件分组，计算滚动 60 秒窗口中的登录失败、4xx、5xx 和高频请求。没有会话和可信来源地址的事件仍能接受单条请求检查，但不进入窗口聚合。

### `src/core/`：共同约定

`constants.js` 放置最大日志行数、规则版本号和告警状态转换表。服务端与分析模块共用这些常量，避免在两处维护不同的版本或状态定义。`hash.js` 计算输入内容的短哈希，用来标识数据集；同一份文本可以得到相同的数据集 ID。

### `src/domain/`：告警长什么样

`alert.js` 负责创建告警对象。每条告警包含规则 ID、规则版本、严重程度、来源、事件 ID 集合、证据摘要、建议，以及初始处置状态 `NEW`。集中创建对象可以保证单条请求规则和窗口规则输出同样的字段。

### `src/server/`：本地接口与持久化

`server.js` 是运行入口。它提供静态页面、示例日志、分析、历史报告和人工处置接口。收到导入请求后，它调用 `src/analysis/analyzer.js`，把完整结果写成 `data/{reportId}.json`。用户更新告警状态时，服务端检查允许的状态转换，并追加操作人、理由和时间。服务只监听 `127.0.0.1`，当前没有多用户身份认证。

## 三、`public/`：用户看到的工作台

| 文件 | 主要职责 |
| --- | --- |
| `index.html` | 定义侧边导航、日志导入区、统计卡片、流量图、告警表和历史记录区。 |
| `app.js` | 读取用户选择的文件，调用本地 API，绘制统计与告警，筛选、分批展示、展开原始证据、提交人工处置并导出 JSON/CSV。 |
| `style.css` | 控制页面布局、颜色、表格、图表和窄屏显示。 |

页面使用文本节点展示日志路径、隔离行和处置理由，避免把日志中的 HTML 或诱导文字作为页面代码执行。浏览器负责展示和交互，规则的最终判断仍在分析模块中完成。

## 四、`fixtures/`、`scripts/`、`tests/`：怎样证明结果可复现

`fixtures/experiment-cases.json` 定义固定的合成会话及其评价标签；`experiment-plan.json` 事先写明实验问题、固定条件、主要指标和判断门槛；`approved-load.json` 是独立的压测批准清单。批准信息不从日志路径或 IP 猜测，标签也不会被送入分析器决定告警。

`scripts/eval.js` 根据固定情境生成日志，分别运行默认 P2-R1 与候选 P2-R2，按完整会话计算 TP、FP、FN、TN、Precision、Recall 和 FPR。运行 `npm run eval` 查看结果；`npm run experiment` 还会把输入、两版报告与结果保存到本地 `data/experiments/`。

`tests/analyzer.test.js` 验证解析、去重、时间窗口和证据关联；`tests/experiment.test.js` 验证两版规则确实只按批准会话改变高频告警处理；`tests/server.test.js` 验证分析报告的保存、读取和人工处置状态转换。运行 `npm test` 可以独立复核这些约定。

## 五、`docs/`、根目录与运行数据

`README.md` 是首次进入仓库的入口，说明如何启动和体验。`package.json` 把 `npm start`、`npm test`、`npm run eval` 和 `npm run experiment` 对应到实际文件。

`docs/` 中，`材料索引.md` 按用途汇总全部交付材料的入口与状态，`project.md` 解释项目边界和输入契约，`rules.md` 写清规则阈值与窗口，`api.md` 说明本地接口和报告字段，`experiment.md` 与 `evaluation.md` 记录实验设计及结果，`release.md` 说明交付恢复，`peer-review.md` 用于结对复核。中文讲解稿和简明报告适合汇报展示，`课程要求对照.md` 把课件要求映射到实现与尚未覆盖的部分，并按章节 04 的四项量规逐项列出证据位置、核对方式与缺口。

`data/` 在首次分析后自动出现，保存用户导入日志生成的完整 JSON 报告。它被 `.gitignore` 排除，不属于源代码。报告可能含原始请求路径和会话标识，因此分享或迁移前应先检查其中的敏感信息。

## 六、用一次导入串起所有目录

1. 用户在 `public/index.html` 的页面选文件，`public/app.js` 读取文本并请求 `/api/analyze`。
2. `src/server/server.js` 接收请求，调用 `src/analysis/analyzer.js`。
3. `src/analysis/parser.js` 和 `normalizer.js` 逐行解析、统一时间、去重并保留隔离记录。
4. `src/analysis/rules/` 检查单条请求与时间窗口，`src/domain/alert.js` 创建带事件 ID 的候选告警。
5. `metrics.js` 与 `report-builder.js` 生成完整报告，服务端将它写入 `data/`。
6. 页面展示统计、原始证据与告警。人工处置请求回到服务端，更新同一份报告中的处置历史。
7. `fixtures/`、`scripts/` 和 `tests/` 从旁验证规则的含义、运行结果和可追溯性。

**建议讲解顺序：**先展示目录树，再沿第六节走一遍导入流程，最后打开一条告警的事件 ID 和处置历史。这样听众能同时理解“文件放在哪里”和“数据为什么经过这些文件”。
