# Web 日志异常与审计程序

一个在本机运行的离线日志分析工具。导入 Web 访问日志后，程序会规范化事件、隔离坏行、检测候选异常，并把告警关联到原始事件。使用者可以分诊、确认或排除告警，保留处置理由与状态变化。本项目对应《AI 原生软件工程实践》中的 P2：Web 日志异常、行为分析与审计。

## 项目背景与目标

Web 服务器会持续产生访问日志，其中既有正常访问，也可能包含连续登录失败、资源探测、异常状态码和带攻击特征的请求。直接翻阅原始日志很难迅速找到相关记录；只给出“可疑 IP”或一个告警数量，又无法说明判断依据。这个项目要解决的是**从原始记录到可复核结论之间的断层**：让分析人员知道某条告警由哪些事件触发、采用哪版规则、还有哪些数据被隔离，以及后来由谁以什么理由处理。

项目定位为教学场景下的单机离线工具。一次导入一份日志，先得到候选异常，再由人核对证据和业务背景。它适合课程演示、小规模日志复盘和规则实验，不承担实时采集、自动封禁或企业级安全运营平台的职责。这里的“异常”指命中当前规则的行为，不等同于攻击已被证实。

## 需求分析

### 使用对象与典型流程

主要使用者是需要复盘访问记录的开发者、安全分析人员和课程评价者。使用者先选择日志文件，检查总请求数、来源数量、状态码分布和异常趋势；随后进入告警列表，按级别、IP、规则或路径筛选；最后根据事件 ID 回查原始记录，决定分诊、确认、排除或关闭。课程评价者还需要使用固定合成数据重跑规则，并核对统计单位、分母和误判记录。

### 功能需求

1. **日志导入与规范化。** 接受 JSONL 及常见 Nginx/Apache 访问日志。统一事件时间为 UTC，解析请求方法、路径、状态码、来源和可选会话字段。旧日志缺失事件 ID 时生成稳定 ID，显式重复的事件 ID 不参与检测。
2. **数据质量反馈。** 对坏行、缺少必要字段、无效时间和重复 ID 给出行号、原因及原始文本。分析不能为了获得更好看的结果而静默删除异常输入；报告要同时说明有效记录数和隔离数量。
3. **规则检测与证据关联。** 逐条请求规则识别常见可疑特征，滚动时间窗口识别集中行为。告警至少包含规则、级别、时间、分组依据、来源、触发事件 ID、证据摘要、建议和规则版本。缺少会话 ID 时允许按 IP 分组，但必须保留这种降级信息。
4. **人工处置与导出。** 告警从新建进入分诊，再由人确认或排除，最后关闭。状态转换要有操作人和理由；JSON/CSV 导出应覆盖完整告警，而不只包含当前页面显示的前 100 条。
5. **可重复评价。** 用带标签的合成会话计算 TP、FP、FN、TN、Precision、Recall 和 FPR。标签只用于评价，不进入检测判断。同一会话必须作为一个统计单位，不能把日志行数误写成检出次数。

### 非功能需求与范围

工具应能在 Node.js 18 及以上环境直接启动，不要求数据库或外部服务。服务只绑定 `127.0.0.1`；日志和报告保存在本机。前端以文本方式显示日志字段，避免把路径中的 HTML 当作页面内容执行。单次导入受 10 MB 请求体与 100,000 行上限约束，避免无界读取。当前版本不提供多用户认证、加密存储和并发写入控制，因此不能直接作为多人共享服务部署。

## 项目架构

程序分为浏览器界面、本地 HTTP 服务、分析器和文件存储四部分。`public/` 负责文件选择、结果展示、筛选与导出；`server.js` 接收请求、调用分析器、保存和读取报告，并检查人工处置的状态转换；`analyzer.js` 负责解析、规范化、去重、统计与规则命中；`data/` 以 JSON 文件保存每次运行的完整报告。`eval.js` 独立构造教学数据并计算会话级评价，不参与实际告警生成。

一条数据的处理顺序是：**导入原始行 → 验证格式与时间 → 规范化事件 → 隔离重复或无效记录 → 按请求及滚动窗口检测 → 生成带事件 ID 的报告 → 人工处置**。分析器不读取 `source_label` 来决定告警，避免把评价答案泄漏给规则。报告以内容哈希标识数据集，以运行 ID 区分分析次数，并写入当时的规则版本。旧报告不会随规则代码更新而自动改写；若需比较新版规则，应对同一输入重新运行并并列检查结果。

这种结构刻意保持简单：页面通过本地 API 使用分析结果，规则代码与 HTTP 路由分离，便于单独测试时间窗口和证据关联。JSON 文件足以支撑单机课程演示，也便于直接检查输出；如果未来需要多用户并发、检索大量历史记录或细粒度权限，就需要重新设计存储与认证层。

## 可行性分析

**技术可行性。** Node.js 自带 HTTP、文件系统、哈希和测试模块，现有实现无需第三方运行依赖。输入格式和窗口规则都有确定的处理步骤，可以用合成日志验证。当前测试覆盖旧新版时间转换、重复 ID 隔离、跨分钟窗口和事件证据关联；这证明核心流程在所列样例下可运行，并不代表已覆盖所有真实服务器日志变体。

**实施可行性。** 项目按“先导入、再检测、后复核”的顺序落地，每一步都有可观察产物：隔离行、规范化事件、候选告警和处置记录。开发者可以先用内置示例检查界面，再用自己的脱敏日志扩展规则。发布只需要代码仓库和符合要求的 Node.js 环境；报告目录由程序在首次分析时创建。

**资源与成本。** 本地运行不需要购买云资源，也没有模型 API 调用费用。主要成本来自人工核对告警、维护规则以及保存和保护日志数据。大量误报会增加复核工作量；因此上线真实业务前，应收集经过授权的业务样本，明确正常压测、爬虫和故障流量，再调整阈值，而不是直接沿用教学默认值。

**风险与边界。** IP 可能代表代理或共享出口，不能据此识别个人。路径、会话标识和原始行可能含敏感信息，当前报告是本机明文 JSON。人工处置里的操作人是填写值，尚无账号认证。规则只能发现已定义的模式，漏报与误报都可能发生；四个合成会话的评价结果只用于展示计算过程，不能作为真实场景的准确率承诺。基于这些边界，本项目对单机离线复盘和教学验收可行，进入多人或生产环境前仍需补充身份认证、权限、数据保护和真实数据校准。

## 快速开始

需要 Node.js 18 或更新版本，无需安装第三方依赖。

```powershell
git clone https://github.com/xjh353/webAutoLog.git
cd webAutoLog
npm start
```

打开 <http://127.0.0.1:3000>，点击「加载示例日志」体验导入、分析、查看证据和人工处置。也可以拖放或选择自己的 `.log`、`.txt`、`.jsonl` 文件。默认只监听本机；要更换端口，可设置 `PORT` 环境变量。

```powershell
npm test       # 解析、去重、时间窗口和证据关联测试
npm run eval   # 回放合成数据，输出逐会话评价与混淆矩阵
```

## 输入格式

推荐使用每行一条记录的 JSONL：

```json
{"event_id":"req-001","event_time":"2026-11-04T02:05:00Z","service":"web","route":"/login","status":401,"latency_ms":18,"session_id":"s-01"}
```

支持 `request_id` 代替 `event_id`，也兼容 Nginx/Apache Common、Combined 日志：

```text
203.0.113.10 - - [04/Nov/2026:10:05:00 +0800] "GET /login HTTP/1.1" 401 1532 "-" "Mozilla/5.0"
```

事件时间统一为 UTC。旧日志缺少事件 ID 时，程序根据数据集哈希和行号生成 ID；缺少会话 ID 时，聚合规则按来源 IP 分组。无效时间、坏行和重复事件 ID 会隔离在报告的 `rejected` 列表中，并保留原始行供复核。单次请求体上限为 10 MB，日志最多 100,000 行。

## 检测与审计

- 请求规则：疑似 SQL 注入、XSS、路径穿越、敏感路径探测和扫描器特征。
- 滚动 60 秒规则：同组内登录失败达 5 次、4xx 达 8 次、5xx 达 5 次或请求总数达 30 次时产生候选告警。
- 证据链：报告保存数据集 ID、运行 ID、规则版本、规范化事件与原始行；告警保存支持它的事件 ID。
- 人工处置：`NEW → TRIAGED → CONFIRMED/DISMISSED → CLOSED`，每步记录操作人、理由、时间和前后状态。告警可筛选，并导出完整 JSON 或 CSV。

阈值用于课程演示，尚未按真实业务流量校准。高频请求可能是获批压测；来源 IP 也不能直接代表个人。告警是待复核线索，不是自动定罪。当前本地版没有账号认证，填写的操作人标识需要结合团队流程核实。

## 项目结构

```text
analyzer.js       解析、规范化、规则检测、证据关联
server.js         本地 HTTP 接口、报告存储、人工处置
public/           页面与交互
eval.js           合成数据的会话级评价
analyzer.test.js  回归测试
docs/             契约、评价、交付和结对复核材料
data/             运行时生成的本地报告（不纳入 Git）
```
